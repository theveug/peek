## Scaling ceiling (full mesh, will eventually bite — parked 2026-07-10: owner explicitly not willing to go SFU anytime soon)

- [ ] **SFU migration path (longer-term, conflicts with "no info held on a server")** — the actual fix for large rooms is a Selective Forwarding Unit: clients send one upload to a media server, which fans it out, turning N×(N-1) mesh connections into N connections total. This is the real answer if room sizes need to grow past the mesh-practical limit, but it's a meaningful architecture shift and a media server is exactly the kind of "thing in the middle" the no-server-storage principle was written to avoid — needs a deliberate decision later, not a casual addition.
- [ ] **Note: TURN doesn't raise the mesh ceiling, it lowers it** — TURN relay doesn't reduce the number of times a stream must be uploaded (each peer connection still gets its own relay allocation), it just reroutes each copy through the relay server. That adds a second, shared bottleneck (the relay's own bandwidth/CPU, split across every active relayed room) on top of each client's own capacity, plus an extra network hop. Keep this in mind when picking participant caps — a TURN-heavy deployment should cap lower than a mostly-direct-P2P one, not higher.

## Security (open items only — patched items are in CHANGELOG.md, most recently the 2026-07-13 sweep #4)

- [ ] **Accepted risk, documented not fixed — saved-code squatting** — the lazy room-recreation path means anyone who ever learned a room code can recreate that room with *their own* password after it empties (and, since the 2026-07-11 lazy-owner fix, becomes its owner — deliberately the same trust level), and `/api/validate-room` returns `valid:true` for unknown codes. A griefer could squat a group's saved code. Acceptable under the current threat model (codes are shared secrets, same as the manual-join flow), but it's a conscious acceptance now, not an oversight. Revisit only if room codes ever become long-lived/advertised.

## Deployment models

- [x] **Accounts / hosted deployments — decided, Phase 1 shipped 2026-09-06.** 2026-09-06 conversation explored whether Peek should ever support an accounts-based deployment alongside the pure-P2P/no-accounts default. Decision: yes, scoped as a **full social layer** (accounts, friends, presence, DMs), built in phases, strictly opt-in per self-hosted deployment — never something Peek-the-project runs centrally (this is what keeps the project itself from becoming a data controller under GDPR/CCPA/etc.; see `CLAUDE.md`'s Design Principles section). Storage engine: **SQLite** — chosen after walking through the actual risk (password-hashing discipline + file permissions determine leak risk, not the DB engine; SQLite's real advantage over MySQL is having no network-facing service for a self-hoster to secure at all) and confirming it works identically for a LAN-only deployment (it's not a network service, so exposure scope is orthogonal to the DB choice). Auth identifier: **username only, no email** — avoids extra PII and an SMTP requirement just to stand up accounts; means no password-reset-by-email in Phase 1 (accepted gap).
  - **Phase 1 (shipped 2026-09-06)**: account storage + auth only — register/login/logout, SQLite-backed, `ACCOUNTS_ENABLED=1`. See `CLAUDE.md`'s "Accounts, Phase 1" Key Conventions entry for the full mechanism (`AuthManager.js`/`authRoutes.js`/`src/server/db/`), guarded by `tests/auth.mjs`. **No UI yet** — API/schema only, deliberately, tested at the protocol level same as `mic-policy.mjs`.
  - [x] **Phase 1b (shipped 2026-09-06): login/register UI** — lobby-level `AccountPanel.js` wiring the existing `/api/auth/*` routes into an actual form, plus a new `GET /api/trust` so the lobby (no WebSocket) can tell whether accounts are even enabled before showing the button. See `CLAUDE.md`'s "Accounts, Phase 1b" entry.
  - [x] **Phase 1c (shipped 2026-09-06): sync color scheme + device selection to account** — owner-requested, scoped to exactly 6 keys (`theme`/`accentHue`/`bgTint`/`camDeviceId`/`micDeviceId`/`speakerDeviceId`), **not** the full ~30-key settings surface or keybinds — don't misread this as "settings sync is fully done." `AccountSettingsSync.js` pushes on change (debounced) and pulls on login, hooking into 6 existing setter functions with zero `SettingsPanel.js` changes. Includes a safety-net fallback (`PeerManager.withDeviceFallback()`) for when a synced camera/mic ID doesn't exist on a different physical machine. See `CLAUDE.md`'s "Accounts, Phase 1c" entry. Remaining settings (keybinds, notification prefs, quality settings, etc.) are a separate future ask if wanted — not scoped here. **Device selection specifically was superseded same-day by Phase 1d below** — it's no longer account-wide.
  - [x] **Phase 1d (shipped 2026-09-06): per-device camera/mic/speaker memory** — owner-reported after using Phase 1c on a phone: account-wide device sync meant a phone and desktop under the same account kept overwriting each other's camera pick. Camera/mic/speaker now live in their own `device_settings` table keyed by `(user_id, device_id)`, `device_id` a random `localStorage` value generated once per browser install (persists across logout, correctly means "this phone" vs "this desktop" regardless of who's logged in). Color scheme stays account-wide, unaffected — it's genuinely meaningful on every device. See `CLAUDE.md`'s "Accounts, Phase 1d" entry.
  - [x] **Phase 2 (shipped 2026-09-06): friends** — a bare add/accept/remove relationship graph (`FriendsManager.js`/`friendsRoutes.js`/migration `0004_add_friendships.sql`), FKs against Phase 1's `users.id`. Still no presence, so the friends list has no visible online/offline state — that's genuinely blocked on Phase 3 below, not an oversight here. See `CLAUDE.md`'s "Accounts, Phase 2" entry.
  - **Security review of the whole accounts branch (2026-09-07, Phases 1–2): no exploitable vulnerabilities found.** Verified rather than assumed, so a future session needn't redo it: every query is `prepare()`d with bound params (no concatenation anywhere, including the `device_settings` upsert); friend authz is enforced in the `WHERE` clause, not JS branching; argon2id at `m=19456,t=2,p=1` (OWASP's recommended minimum, confirmed by running the hasher); session tokens are 32 random bytes stored only as SHA-256 with real server-side revocation on logout. **CSRF is blocked by two independent layers** — `SameSite=Lax` *and* the fact that only `express.json()` is mounted (no `urlencoded`), so a cross-site HTML form can't produce a parsed `req.body` while a JSON `fetch` fails preflight; **don't add `express.urlencoded()` without re-checking this.** The `COLLATE NOCASE` unique index on `users.username` is load-bearing: it catches the register TOCTOU race across the `await hash()` gap that the app-level `SELECT` alone would miss. Settings pulled from the server are safe sinks (`setTheme()` only `===`-compares; `setAccent()` hard-allowlists against `PRESETS`) and are self-scoped anyway. Accepted/documented low-severity items: username enumeration (register's 409, friends' `not_found`) and `secure: req.secure` leaving the cookie non-`Secure` on plain-HTTP LAN (already warned about at startup). The one real gap found was the missing account-level blocklist — tracked in the Security section above.
  - [x] **Phase 3 (shipped 2026-09-07): presence, poll-based** — originally scoped during Phase 1 planning as needing a genuinely new always-on connection; a 2026-09-07 security/load review revised that to **poll first, not a socket** (numbers and reasoning in `CHANGELOG.md`'s Accounts section), and this ships exactly that plan: `GET /api/friends/presence` (`friendsRoutes.js`), polled every 30s by `presencePoll.js` while a logged-in user has the lobby open. **The poll call is its own heartbeat** — `AuthManager.touchLastSeen()` runs as the route's side effect, so there's no separate heartbeat endpoint; "online" is derived at read time (`FriendsManager.listFriendsPresence()`, `last_seen_at` within a 90s threshold — 3x the poll interval, tolerates one missed beat). Client: a small dot on each `FriendsPanel.js` friends-list row, fed by `lobby.js` starting/stopping the poller on the existing `peek:account` event. **Deliberately minimal — don't read this as full presence**: lobby-only (no room-page presence; `AccountPanel.js`/`FriendsPanel.js` don't exist on the room page today), no "last seen \<time\>" text, no away/idle distinction — just online/offline. See `CLAUDE.md`'s "Accounts, Phase 3" entry. Guarded by `tests/presence.mjs`.
    - **The persistent-socket path from the original plan was deliberately NOT built** — defer it until Phase 4 (DMs) actually needs push delivery, the feature that genuinely can't tolerate polling. If it ever is built, the three non-negotiables from the review still apply: (1) **validate the `Origin` header on the WS handshake** (WebSocket handshakes have no CORS enforcement — a cookie-authenticated socket needs this even though the current room socket doesn't, since that one carries no ambient authority); (2) **derive the recipient list server-side from the DB at send time**, never from a client-subscribed list (`users.id` is a sequential integer already exposed in `/api/friends`, trivially enumerable); (3) **invalidate on unfriend** — a cached connect-time subscription would keep an ex-friend receiving presence until they reconnect.
    - **Privacy, decided deliberately, not shipped quietly**: presence is the first feature that *continuously generates new data about a person's habits just by existing* — accounts store what someone typed, presence infers when they're at their desk, and with `DEBUG=1` or any reverse-proxy access log an operator can reconstruct daily activity patterns. Revisit whether the trust badge should surface this explicitly (today it only reflects `trust.accounts`, not presence specifically).
    - Reconnect jitter for `App.js`'s room-socket reconnect: **shipped 2026-09-07** — `setTimeout(connect, 2000)` is now `2000 + Math.random() * 2000`. See `CHANGELOG.md`'s Rooms section.
  - [x] **Phase 4 (shipped 2026-09-07): direct messages, poll-based, plain-text.** Originally scoped as needing Phase 3's connection to feel real (push delivery, not a poll) — since Phase 3 shipped poll-based instead (see its own entry above), Phase 4 follows the same pattern rather than being the thing that finally justifies the socket: `messagesPoll.js` polls `GET /api/messages` every 30s for the inbox/unread badge, same shape as `presencePoll.js`. New `direct_messages` table (migration `0007_add_direct_messages.sql`: `sender_id`/`recipient_id` FK `users.id`, `body`, `created_at`, nullable `read_at`) — `DirectMessagesManager.js`/`messagesRoutes.js` (`GET /api/messages`, `GET /api/messages/:username`, `POST /api/messages/:username`). Friends-only, re-checked on every send (not just at conversation-open) — `sendMessage()` calls the same accepted-friendship check `FriendsManager` uses, so blocking someone (which already deletes the friendships row) transparently blocks new DMs too with no separate check needed; unfriending preserves existing message history but blocks new sends. **`trust.serverSideHistory` flipped to `true`** (tied to `accountsEnabled`, not a separate flag — DMs only ever exist under that same opt-in) — `tests/trust-tier.mjs` updated to match. Client: `MessagesPanel.js` (lobby-only popover, inbox + conversation-thread views), reachable via its own topbar button or a new "Message" action on `FriendsPanel.js`'s friend rows (cross-popover via a `peek:open-dm` `CustomEvent`, same shape as `peek:account`). Guarded by 24 `tests/messages.mjs` assertions plus a real two-browser-context Playwright pass (cross-panel deep-link, send, inbox preview, unread badge, mark-as-read, reply round-trip — zero page errors). See `CLAUDE.md`'s "Accounts, Phase 4" entry for the two deliberate v1 scope cuts below.
    - [x] **Scope cut revisited (2026-09-09): DM composer now has feature parity with room chat's code blocks + emoji.** Owner-reported: "can we not reuse the same input area as chat so we get all the other features too like code blocks and emoticons." `MessagesPanel.js`'s composer gained the same "+" menu (code-block language picker, emoji picker) as the room composer, and `_renderThread()` now renders via the identical `marked` → `DOMPurify` → `finalizeCodeBlocks()` pipeline `ChatUI.js` uses (not a new attack surface — the same already-audited pattern, just applied to a second surface) **when the vendor libs are available**, falling back to the original plain-`textContent` path otherwise. **Still not full parity, deliberately**: `marked`/`DOMPurify`/`highlight.js` are only loaded on the room page (`index.html`) — `lobby.html` never loads them, so a DM sent from or viewed in the lobby's Friends & Messages drawer still renders plain text and has no "Code block" +-menu option (hidden entirely there), rather than growing the lobby's initial page weight for a feature only reachable after logging in and adding a friend. ## Collaboration

- [ ] **Rejected: local contacts / friends list** — considered a client-side contacts system (local keypair + `localStorage` label per contact, added via out-of-band invite link, no server directory/discovery). Dropped because without accounts there's no cross-room presence, so "friending" someone only pays off if you can PM them outside a room — and *that* needs presence tracking, a bigger step against no-server-storage than a contacts list justifies. **Saved rooms** (see `CHANGELOG.md`) covers the actual need. Revisit only if async P2P messaging becomes a real goal — see Direct messaging below.
- [ ] **Direct messaging (P2P data channel)** — deprioritized 2026-07-10: owner considers this moot without a friends/contacts list (rejected above), since in-room-only DMs don't cover the real use case. Keeping the technical sketch in case that changes: private 1-to-1 chat between any two participants via `RTCDataChannel` on the existing peer connection, so messages never touch the signaling server. Click a participant's avatar/name to open a scoped DM panel alongside group chat. Implementation lives in `PeerManager.js` (open a named data channel per peer on connect, handle `ondatachannel` on the receiving side). Works identically in the hosted web version and the future Electron build since data channels are P2P after ICE.

## New feature ideas (brainstorm — 2026-07-04)

Not yet scoped/estimated — captured here so they don't get lost; move into a proper section once someone picks one up.

- [ ] **Rejected: live captions** — considered a Web Speech API overlay, but Chrome's implementation actually relays audio to Google's cloud speech service (not on-device), which conflicts with the offline/no-third-party-request standing rule; a real on-device alternative (bundled Whisper via WASM) is a much better accent-accuracy fit for NZ English but adds 40-150MB of model weight and real CPU cost on top of an already-live call. Dropped for now — more bloat than the tool wants to carry at its current size, not worth it just to add captions. Revisit only if a lightweight on-device option becomes practical.
- [ ] **Collaborative whiteboard** — freestanding draw canvas (not just an overlay on a shared screen) synced via the existing data-channel broadcast pattern used for chat/reactions.
- [ ] **Rejected: voice messages** — Peek rooms are live voice calls, so async voice clips have no real use case here (owner confirmed; heavy Discord user who never uses them).
- [ ] **Members sidebar unused space — partially addressed (2026-07-15)** — the raised-hands queue (see `CHANGELOG.md`) now occupies the space below the participant list while relevant, but it hides when nobody's hand is up, so the bottom half still sits empty in the common case. Call-status/bandwidth stats remains floated-and-set-aside (more a power-user/debug stat than permanent-sidebar material, see `DebugPanel.js`). Keeping as a low-priority flag.
- [ ] **Export/import settings (2026-08-25)** — a Settings → Privacy & P2P button to download a JSON blob of local prefs (nickname, keybinds, theme/accent, custom statuses, saved rooms) and re-import it on a new browser/device, fully client-side, no server involvement. Main design question: saved-room passwords are already stored plaintext in `localStorage` (accepted risk while it stays in-browser, per CLAUDE.md's saved-rooms note) but a downloadable file is a bigger exposure surface (email, cloud sync, Downloads folder) — should exclude passwords from the export by default, with an explicit opt-in + warning for anyone who wants a fully portable backup. Considered and rejected a "don't save the password at all" alternative — that just reopens the exact "forgot my room password" pain point saved rooms exists to solve, since there'd be nothing to fall back on on a fresh browser either.

## Accessibility

- [ ] **Broader ARIA/keyboard-nav pass (2026-07-14)** — the two "totally unreachable via keyboard" gaps (`#controls`, per-peer `.participant-actions`) and the Settings/lightbox focus traps are fixed (see `CHANGELOG.md`), but the audit that found them also found near-zero `role`/ARIA usage elsewhere in app code. Remaining, lower-urgency (things are reachable, just not well-described/navigable): custom popovers/menus (moderator kebab, quick-settings, invite, topbar identity, emoji picker, pinned/search panels) have no `role="menu"`/`aria-expanded`/arrow-key navigation — Escape-to-close already works consistently across all of them, this would just make them read/operate more like native menus for screen-reader and keyboard users. Drag-to-reposition self-view PiPs have no keyboard equivalent (mouse/touch only via Pointer Events). No concrete plan yet — flagging scope, not estimating.

## Bigger features (post-Electron)

- [ ] **Multiple rooms/channels (Discord-style)** — basic multi-room already works (`SessionManager.js` keys sessions by room code, anyone can create any number). What's missing for a real "server" feel is a *persistent* list of named channels you can browse and return to — today everything's in-memory and disappears on server restart. Would need an actual storage layer (even lightweight like SQLite) before this is worth building.
